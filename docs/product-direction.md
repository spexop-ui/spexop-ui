# Product direction: local UI/UX companion

Decision: 27 October 2026. This owner-approved decision supersedes the earlier verification-only direction in [ADR-023](adr/0023-local-ui-companion.md). Spexop is a local-first, free OSS desktop companion coordinating **UI/UX development**. The user's main conversation stays with an existing strong coding agent. That agent owns planning, architecture, design judgment, risky decisions and oversight. Spexop is a small execution and evidence loop, not another chat IDE or general PM/multi-agent platform.

## R1: one narrow end-to-end slice

One local project, one active milestone, minimal gates and tasks, a product-runtime LLM API worker boundary, and one main-agent interface. The product worker is distinct from Codex/Astra agents and workers developing Spexop. Selecting a product API provider is not a prerequisite for those development agents to start implementation. A real external acceptance run eventually requires an explicitly authorized live product worker. Begin with one Button/Input/Select scenario. Expansion requires External Product Acceptance of this slice.

1. The main agent gives a bounded routine UI task with allowed files, expected behavior, allowed run/time/token limits and stop conditions. These limits are the task budget; Spexop is not a billing, subscription or budget-management product. Spexop schedules background execution only within that scope. Worker changes are isolated and reviewable; workers cannot widen permissions or accept their own work. No silent paid fallback.
2. Spexop maintains minimal Milestone/Gate/Task status and a simple desktop view of progress, blocked reason and needs-user-action state. A loopback browser panel is an internal prototype, not evidence of a packaged, usable desktop companion. Desktop acceptance requires an installable private build that stays visible or is readily accessible during a task, resumes correct status after restart, and clearly exposes progress, blocked reason and required user action in the consumer environment.
3. Deterministic checks independently verify output; use real-browser Playwright where rendered UI or interactions require it. Bind evidence to revision, environment, check and artifact. Report PASS, FAIL or UNKNOWN. A required skipped/unsupported check, unavailable browser or stale/incomplete evidence is UNKNOWN and blocks its gate. A genuinely NOT_APPLICABLE optional check is excluded from gate evidence and does not block it; it is never counted as PASS. A completed failing check is FAIL.
4. G-VERIFY is the internal technical gate for task scope, deterministic/browser checks and revision-bound evidence in the Spexop development repository. External Product Acceptance is a distinct gate. Install a versioned, privately distributed test package/build in a **separate consumer UI repository**, start a **fresh coding-agent context** without Spexop-development instructions or history, and exercise the authentic end-to-end user flow: strong main agent plans, authorized product API worker executes bounded UI work, Spexop tracks gates, independent checks report PASS/FAIL/UNKNOWN, and the desktop handles progress, blocked and needs-user-action states. Include negative paths and bind evidence to package version, consumer revision, environment and check artifacts. Internal unit/build/Playwright PASS never substitutes for this gate. The owner records acceptance after reviewing the external evidence; release approval is separate.
5. Report API gaps without building a general backend. Free models and their prices/availability are external conditions, not promises or mandatory dependencies.

## Reuse and boundaries

Preserve and reuse Theme, Canonical Model, Foundation Capture, provenance, CSS Export, Build Evidence and tests where useful. CSS Export and Build Evidence are not R1 prerequisites. Historical verification NO-GO evidence keeps its original scope. Protect secrets and local files with least privilege, scoped permissions and redacted logs. No mandatory paid API, cloud, SaaS, extra dashboard, new renderer or DS generator.

Observe → Verify → Feedback → agent fixes → retest remains a verification step inside this companion workflow, not the whole product. Project consistency and executable contracts remain conditional later research. Public repo, npm, deployment and release require separate security, rights, provenance and owner decisions.
