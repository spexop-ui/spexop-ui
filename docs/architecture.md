# Local companion architecture boundary

This is the owner-approved target, not an implemented system. The existing strong coding agent is the primary user interface and owns planning, architecture, UI/UX judgment, risk and oversight. Spexop exposes a small local handoff/evidence interface. Its desktop surface shows one active milestone, current task, gate state, progress, blocked reason and needs-user-action state.

The first slice has one local project, one active milestone, a minimal Gate/Task ledger, a product-runtime API worker boundary and one main-agent interface. Product-runtime LLM workers are separate from the Codex/Astra agents and workers that develop Spexop; provider selection does not block development. A task contract specifies allowed paths, requested UI behavior, allowed run/time/token limits, stop conditions and acceptance checks. These limits are a task budget, not a billing or subscription feature. Background scheduling starts only authorized bounded work, with no silent paid fallback. Worker changes stay isolated and reviewable. Secrets remain local and redacted; permissions are explicit and scoped.

Verification is Observe → Verify → Feedback → main-agent fix or bounded worker retry → retest. G-VERIFY is the internal technical gate. Deterministic checks and real-browser Playwright, when required, bind outcomes to source revision, route, viewport, fixture, check version and artifact. Every required check reports PASS, FAIL or UNKNOWN with reasons. Required skipped/unsupported checks, missing browser access and stale/incomplete evidence are UNKNOWN; an executed failure is FAIL. Genuinely NOT_APPLICABLE optional checks are excluded from the gate, never PASS evidence. The ledger records evidence and acceptance authority separately.

External Product Acceptance is a second gate after internal technical verification. A versioned private test package/build is installed in a separate consumer UI repository; a fresh coding agent without Spexop-development instructions or history performs a real user flow with an authorized live product API worker. Evidence binds package version, consumer revision, agent context, task limits, environment, checks and artifacts. The flow includes planning, bounded execution, gate tracking, independent verification, desktop status and blocked handling, plus negative paths. A loopback browser panel merged in PR #13 demonstrates an internal status prototype only. Desktop acceptance requires an installable private companion that remains visible or readily accessible during a task, survives restart with accurate status, and makes progress, blocked reason and user action clear. No public npm release is needed for the private acceptance run.

API availability, model cost/limits and handoff capabilities must be probed and reported as gaps. Do not create a general backend, chat IDE, cloud coordinator or broad multi-agent system to work around a gap. Existing Theme/Foundation assets may be reused under their provenance and license boundaries; CSS Export and Build Evidence are optional for R1. Their historical NO-GO findings remain intact.
